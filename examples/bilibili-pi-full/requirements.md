你正在通过 pi + DeepSeek 实际试用 Code Normify 架构工具。请直接调用 MCP 工具完成设计与保存。不要只回答方案或伪造调用结果，不编写业务代码。

## 用户的原始需求

“完全仿照 bilibili 做一个视频网站。用户提供服务器、RDS（数据库服务器）、OSS，没有视频资源，需要自行获取。要看架构图、数据结构图，尤其是如何拆给不同 Worker。”

目标是完整产品的目标架构，不要偷换成首页和播放页、简化版、MVP。功能与体验对标，不复制商标、源码或私有数据。所有模块处于设计 planned 状态。本次不访问真实服务器/RDS/OSS，不进行视频下载或部署；内容获取能力须完整纳入设计。

## 现有资源与明确待定项

- 服务器：承载应用、媒体处理和后台任务；配置、数量、地域未给出，资源状态标记为用户已提供、连接参数待配置，不假定无限容量。
- RDS：事务数据、目录、用户、账本、任务和 outbox；数据库引擎尚未指定，先定义统一关系模型，实施前明确方言，禁止猜测切换引擎。
- OSS：原始视频、转码产物、封面、字幕、直播回放。配置和 bucket 连接参数待配置。
- Redis/MQ/搜索服务/CDN/RTC/支付/短信不是用户已提供资源；标记为待接入的适配器或服务器上部署的组件。队列可明确设计为 RDS outbox+job lease，后续 MQ 是显式迁移，不是运行时猜测兜底。
- 视频资源从创作者投稿、明确许可的视频源和可追溯导入流程获取。设计许可证据、来源、下载任务、去重、归属和审核，不把现成 bilibili 视频库写成已有资源。

## 先冻结的核心契约

- ID 统一字符串，时间统一 UTC ISO，金额统一最小货币单位整数，分页和错误只有一种形态。
- Video 与 MediaAsset 分离；媒体处理、审核和发布三个状态机分开；Catalog 拥有唯一发布命令。
- 投稿主链：上传→OSS 原件→媒体处理/转码/封面/字幕→审核→发布事件→搜索/推荐/动态等投影。
- 所有播放入口消费统一 PlaybackGrant，核验可见性、版权和会员权益再签发播放地址。
- 写操作有幂等键；异步事件有版本、生产/消费模块、去重和失败处理。支付/礼物/收益使用独立账本。
- 每张 RDS 表只有一个业务写入所有者，索引/统计/动态列表是事件投影，禁止不同 Worker 绕过领域 API 改表。
- 每个 Worker 的后端、前端功能、迁移与测试目标文件独占。共享契约及集成文件由单独 Worker 管理，业务 Worker 并行前先冻结契约。

### 架构服务器 architecture

1. 先用 normify_help 或 schema 获取工具参数，normify_graph_get 获取空图及 digest。
2. 设计完整模块树、命名 JSON Schema 类型、API input/output 和出向依赖。模块 tags 标明唯一 worker:<owner>；Worker 标识须稳定。共享契约 Worker 单独维护共享包。后端、前端、部署和迁移均有明确职责。
3. 所有 Module 必填字段遵循工具 Schema：uid=独立唯一 8 位小写 hex，id=小写点分模块名，parent=直接父 id 或根的 null，name/description={zh,en}；source=[{path:未来目标相对文件路径}]；revision=40 个 0；updated_at=UTC ISO；fingerprint=pending；state=planned。容器/根不含 apis/types，叶子 apis 必填（可为空数组）。类型名符合 TypeScript identifier。
4. 类型使用合法 JSON Schema 2020-12；跨类型 $ref 统一 urn:normify:<module-id>:<type-name>，API 引用固定 {module,name}。请求/响应和事件必须有真实字段、必填、枚举等约束，不能用空 object 或一句 TODO 占位。
5. source 是文件不是目录，每个 Worker 目标路径独占；把各领域前后端/migrations/tests 按 feature 目录划分。禁止多个 Worker 共享 app.ts/routes.ts/schema.sql 等可写文件。
6. deps 指向确实存在的模块，写明调用/事件/数据流/引用语义；接口边可带真实 from_api/to_api。共享类型、存储适配器和事件总线不反向依赖业务模块，避免循环调用。选主线连接，不绘制无意义的全互连。
7. 为每个容器设计 layouts，根层使用分组或网格，max_columns<=4，提供双语 reading/order；顶层能看出客户端、业务域、数据契约、基础设施。不要让几十个叶子挤在同一层。
8. normify_graph_validate 校验完整候选并修正全部 error，随后 normify_graph_put({graph,expect_digest}) 保存并生成 HTML。全图须保留需求范围，不把无法实施的外部资源标成已落地。
9. 使用 normify_work_packet 对每个稳定 Worker 负责的模块集合取得实现包，要求无文件冲突，保存当前冻结 digest 的分工证据。可用工具结果确定拆分是否实际成立，不能只写一张分工表。

### 数据服务器 data

1. 单独生成数据结构视图，使用同一种 Normify graph Schema。不要用另一套伪字段结构替代 JSON Schema。
2. 根为 data，按领域分层，每个实体叶子只声明一个完整实体 types[] Schema。涵盖上述所有功能；不要只画 User/Video/Comment 三张表。容器不声明 types/apis。
3. entity Schema 的 properties、required、enum、format、description 完整说明字段；schema.description 和字段 description 明确 RDS/OSS/搜索投影归属、表名、主键、外键、唯一约束/复合唯一约束和索引。数据库跨行约束属于实施契约，JSON Schema 不宣称已代替 RDS 外键校验。
4. 实体间关系使用 deps(kind=reference)，label 明确外键字段和基数，如“authorId → User.id，多对一”。关系必须指向确实存在的实体。关联表显式建模，账本、许可证据、转码版本、审核、订单、直播、任务和 outbox 不能省略。
5. data entity tags 包含对应 worker:<owner>、storage:rds/oss/search 的明确归属；source 指向唯一计划模型/迁移文件；所有实体 planned。OSS 对象是对象元数据，不把视频二进制写进 RDS。
6. 类型/实体与架构契约的命名及语义一致。为容器给出清晰布局、阅读说明和适量关系连线。
7. normify_graph_validate 修正所有 error，normify_graph_put 保存和渲染。
